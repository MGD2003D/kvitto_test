## Где модель ошиблась
- **Потерянное решение.** После перезапуска сессии план вернулся с `payment_id: int`,
  хотя договорились об UUID для платежей. Заметил при ревью плана.
- **Тест, который ничего не проверял.** Для корректной работы SAVEPOINT (на нём держится идемпотентность)
  тестовой SQLite нужна специальная настройка; Postgres в проде она не нужна. Первый тест агента проходил
  одинаково с ней и без неё, то есть её не проверял. Был добавлен тест, который не проходит если эта настройка отсутствует.
- **Commit после ответа.** Коммит стоял в зависимости после `yield` — этот паттерн предложил
  ИИ-ассистент. Начиная с FastAPI 0.118 код после `yield` выполняется уже после отправки ответа:
  клиент мог получить 201, а при упавшем commit платежа в базе не было бы. Исправлено через
  `Depends(get_db, scope="function")`, добавлен тест: упавший commit → 500 и платежа нет.
- **После ревью** Код-ревью отдельным агентом в чистом контексте нашло две ошибки,
  которые не ловили тесты:
  - гонка вебхуков: два одновременных вебхука для одного платежа оба, проходили проверку смены статуса
    и получали 200, итоговый статус зависел от того, кто закоммитит последним. Исправлено условным
    `UPDATE ... WHERE status = :current`: если статус уже изменился, обновляется 0 строк и ответ 409;
  - `tariff_id` больше 2³¹ − 1 давал 500 на Postgres (не влезает в `INTEGER`). Добавлено ограничение
    в схеме, теперь 422.

  Отклонил два замечания агента: 
  1. Не стал повторять проверку рассрочки в сервисе — её уже делает API,
  а две копии правила со временем разойдутся; 
  2. Неизвестный статус в базе оставил ошибкой 500,
  а не 409 — это поломка данных, её нельзя прятать за обычным отказом.
