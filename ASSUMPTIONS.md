# Допущения

Решения по вопросам, которые ТЗ не покрывает или покрывает неоднозначно.
Формат: что в ТЗ → что сделано и почему → как было бы правильнее в проде (если отличается).

## 1. Повтор `Idempotency-Key` с другим телом

- **ТЗ:** «если платёж с таким ключом уже есть — вернуть его с кодом 200», про тело ничего.
- **Сделано:** тело не сравнивается, возвращается ранее созданный платёж (200) — буквальное ТЗ.
- **В проде:** хранить хеш тела и при несовпадении отвечать ошибкой (как Stripe): иначе клиент с ошибкой
  в коде успешно получит старый платёж вместо нового.

## 2. Область действия `Idempotency-Key`

- **ТЗ:** заголовок необязателен, формат и длина не указаны.
- **Сделано:** ключ уникален глобально; пробелы по краям обрезаются, пустой ключ = нет ключа; длина до 255 (колонка `VARCHAR(255)`).
- **В проде:** ключ уникален в пределах аутентифицированного клиента — сейчас, без авторизации, чужой
  совпавший ключ вернёт чужой платёж. Для создания платежа ключ стоит сделать обязательным.

## 3. Идентификаторы

- **ТЗ:** тип id не указан.
- **Сделано:** платежи — UUID (последовательный id позволял бы перебирать чужие платежи, авторизации нет);
  тарифы — int 1/2/3, засеваются миграцией.

## 4. Входные данные платежа

- **ТЗ:** `installment_months` обязателен для рассрочки (3, 6 или 12); для card/sbp и про пустой промокод ничего не сказано.
- **Сделано:** у card/sbp пустое `installment_months` (`null`) допустимо, а указанный срок рассрочки — ошибка 422:
  у оплаты картой или СБП рассрочки быть не может. Пустой промокод = без промокода.

## 5. Пагинация `GET /payments`

- **ТЗ:** только фильтры `email` и `status`.
- **Сделано:** `limit` (по умолчанию 50, максимум 100) и `offset`, порядок `created_at desc, id desc` —
  иначе список растёт вместе с базой.

## 6. Повтор вебхука с тем же статусом

- **ТЗ:** «остальные переходы запрещены».
- **Сделано:** `succeeded → succeeded` — 409, строго по ТЗ.
- **В проде:** банки повторяют вебхуки, поэтому повтор текущего статуса обычно отвечают 200 без изменений.
