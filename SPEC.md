# SPEC — Kvitto Payments API

Сервис, через который онлайн-школа принимает оплату курса: тарифы, создание платежа,
просмотр платежа и уведомления банка о смене статуса.

## Тарифы

Хранятся в таблице `tariffs`. Начальные тарифы создаёт отдельная data-миграция Alembic
(`op.bulk_insert`), она применяется при старте вместе с остальными миграциями (`alembic upgrade head`).
Засев в коде приложения (lifespan) не используется. Изменение цен — новой миграцией.
В тестах тарифы вставляет фикстура.

| id | title    | price (копейки) |
|----|----------|-----------------|
| 1  | basic    | 990000          |
| 2  | standard | 1990000         |
| 3  | premium  | 2990000         |

`id` тарифов — целые числа, засеваются явно (1, 2, 3).

## Деньги

- Все суммы в API и в БД — целые числа в копейках: 19 900 ₽ → `1990000`. `float` не используется.
- Промокод `KVITTO10` даёт скидку 10% от цены тарифа, регистр не важен.
  `discount = price * 10 // 100`, `amount = price - discount`.
- Пустой промокод (`""` или строка из пробелов) равносилен отсутствию промокода; пробелы по краям обрезаются.
- Неизвестный промокод — 422 (валидация в схеме Pydantic, стандартный формат FastAPI).

## Способы оплаты и рассрочка

- `method`: `card` | `sbp` | `installment`.
- Для `installment` обязателен `installment_months` ∈ {3, 6, 12}. Для `card`/`sbp` поле можно не передавать
  или передать `null`; любое другое значение — 422. Правило проверяет схема Pydantic, сервис его не дублирует.
- График: `amount` делится на срок в копейках. Сумма всех платежей графика строго равна `amount`,
  лишние копейки — по одной в первые платежи. Даты платежей не нужны.
- Для `card`/`sbp` `schedule = null`.

Пример: standard без промокода, рассрочка на 3 месяца →
`amount = 1990000`, `schedule = [663334, 663333, 663333]`.

## Статусы

- Новый платёж — `pending`.
- Допустимые переходы: `pending → succeeded`, `pending → failed`, `succeeded → refunded`.
- Все остальные переходы запрещены, включая повтор того же статуса.
- Смена статуса — условный `UPDATE ... WHERE id = :id AND status = :current`: из двух одновременных
  переходов из одного статуса применяется один, второй получает 409.
- В БД хранятся только эти четыре статуса; другое значение — порча данных (500, не 409).

## Эндпоинты

### `GET /tariffs`
200 — `[{id, title, price}]`.

### `POST /payments`
Тело: `tariff_id`, `email`, `method`, `installment_months` (для рассрочки), `promo_code` (необязательно).

- 201 — платёж создан.
- Заголовок `Idempotency-Key` (необязательный): если платёж с таким ключом уже есть — вернуть его с кодом 200, второй не создавать.
  Тело повторного запроса с тем же ключом не сравнивается: возвращается ранее созданный платёж.
  Ключ хранится в колонке с unique-ограничением; при гонке (IntegrityError) вернуть существующий платёж.
  Пробелы по краям ключа обрезаются; пустой ключ равносилен отсутствию заголовка.
  Длина ключа после обрезки — не больше 255 символов, длиннее — 422.
- `tariff_id` — целое от 1 до 2³¹ − 1, вне диапазона — 422. Несуществующий `tariff_id` — 404.

### `GET /payments/{id}`
`id` — UUID. 200 — платёж; 404, если его нет; 422, если `id` не UUID.

### `GET /payments`
200 — список платежей. Необязательные фильтры `email` и `status`, комбинируются. Неизвестный `status` — 422.
`email` нормализуется так же, как при создании платежа, и сравнивается точно; невалидный email — 422.
Пагинация: `limit` (1–100, по умолчанию 50) и `offset` (≥ 0, по умолчанию 0). Порядок — новые первыми
(`created_at desc, id desc`).

### `POST /webhooks/bank`
Банк сообщает о смене статуса. Тело: `payment_id` (UUID), `status`.

Порядок проверок:
1. Подпись. Заголовок `X-Signature` — hex HMAC-SHA256 от сырого тела запроса с секретом из переменной `WEBHOOK_SECRET`.
   Сравнение через `hmac.compare_digest`. Неверная или отсутствующая подпись — 401.
2. Тело невалидно (битый JSON или тело не в UTF-8, `payment_id` не UUID, неизвестный `status`) — 422 в стандартном
   формате FastAPI (`loc` начинается с `"body"`, у битого JSON — `["body", <позиция>]`).
3. Платежа нет — 404.
4. Запрещённый переход — 409 с телом ровно `{"error": "invalid_transition"}`, статус не меняется.
5. Успех — 200 `{"result": "ok"}`.

## Формат платежа в ответах

`id` (UUID), `status`, `tariff_id`, `amount`, `discount`, `method`, `installment_months`,
`schedule` (список сумм в копейках или `null`), `email`, `created_at` (UTC, с таймзоной).

Ошибки валидации — стандартный ответ FastAPI с кодом 422, свой формат не нужен.

## Тесты (обязательные сценарии)

Тесты проверяют результат, а не только код ответа.

- Сумма с промокодом и без, в том числе промокод в нижнем регистре.
- Сумма графика равна сумме к оплате для 3, 6 и 12 месяцев (в том числе со скидкой).
- Повтор с тем же `Idempotency-Key` не создаёт второй платёж: тот же `id`, код 200, в БД одна запись.
- Запрещённый переход возвращает 409 с `{"error": "invalid_transition"}`, повторный `GET` показывает прежний статус.
- Запрос несуществующего платежа возвращает 404.
- Подпись вебхука: верная, неверная, отсутствует.
- Фильтры `GET /payments`.

## Вне скоупа

Фронтенд, авторизация пользователей, реальная интеграция с банком, деплой.
